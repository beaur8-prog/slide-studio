# Slide Studio — PowerPoint 레이아웃 정확도 개선 계획

- 작성일: 2026-11-04
- 검토한 소스: Slide Studio **1.6.22**, 커밋 `fd5a04cd77b49e70de5d1734f814e97a41b0e856`
- 상태: **첫 작업 묶음 완료 — 비교 기반과 일반 양쪽 맞춤 보완, 전체 계획은 후속 작업 남음**
- 계획 작성 시 검토(2026-11-04): 소스, 기존 비교 기록, 자동 검사와 Microsoft 공식 문서. 당시에는 화면 비교·회귀 검사를 새로 수행하지 않았다. 2026-11-05의 실제 작업 결과는 10절에 별도로 기록한다.

## 1. 목표와 권장 순서

가장 먼저 **같은 글꼴에서 문단 정렬·탭·줄바꿈이 달라지는 문제**를 줄인다. 이어서 자동 맞춤과 표 높이, 차트 내부 배치, 복합 도형의 순서로 개선한다. 모든 단계에서 **저장한 PPTX를 PowerPoint로 다시 열었을 때의 외관**까지 확인한다.

현재 앱에는 원본 XML·미디어를 보존하는 기반이 있다. 다음 작업의 중심은 이를 교체하는 것이 아니라, 원본 속성을 편집 모델과 화면에 더 정확하게 반영하는 것이다.

| 순서 | 작업 | 사용자에게 보이는 효과 |
| --- | --- | --- |
| 1 | 현재 버전의 PowerPoint 비교 기준과 재현 자료 고정 | 수정 전후를 같은 조건으로 판정 |
| 2 | 양쪽·분산 정렬, 사용자 지정 탭, 실제 글꼴 진단 | 본문 정렬, 숫자 열, 줄바꿈의 차이 감소 |
| 3 | 자동 맞춤·줄 간격과 표 높이 계산 정밀화 | 긴 문장 잘림과 불필요한 표 확장 감소 |
| 4 | 마스터·레이아웃 상속 및 저장 후 의미 보존 점검 | 템플릿 자료와 편집 후 재열기의 외관 유지 |
| 5 | 차트의 명시적 배치와 글자 크기에 따른 자동 배치 | 축·범례·제목·데이터 라벨의 위치 개선 |
| 6 | 비균일 그룹 변환, 도형 내부 채움과 효과 | 복잡한 도표의 기울기·무늬·그림 표시 개선 |

이 계획은 정적인 슬라이드 외관과 편집·저장 후 외관을 대상으로 한다. 애니메이션 타이밍, 오디오 재생, 마스터 편집 UI 확대는 별도 과제로 관리한다. 미설치 글꼴이나 Office 고유 자동 배치까지 완전히 동일하다는 목표를 전제하지 않는다.

## 2. 현재 상태: 이미 해결한 것과 남은 것

### 기존 성과와 증거의 범위

2026-10-31 기록에는 공개 자료 20개·93장 중 이미지 위주의 31장을 분리하고, **편집 가능한 개체가 있는 17개·62장**을 웹 PowerPoint와 비교한 결과가 있다. 사진 자리표시자, 표 테마색·대각선, 차트 색·라벨, 그림 배경, 일부 레이더와 SmartArt 표시 등을 개선했다.

저장 후보 9개가 웹 PowerPoint에서 복구 경고 없이 열린 기록도 있다. 다만 **저장본의 모든 장을 다시 시각 비교한 결과는 아니다.** 기존 755개 회귀 검사 통과 같은 수치도 당시 기능 검사 결과이며 현재 버전의 외관 일치율이 아니다.

이미 구현된 항목은 새 기능으로 다시 계산하지 않는다.

- 원본 글꼴 우선 사용, 한영 글꼴 별칭, 사용자 추가 글꼴, 일부 기존 Office 글꼴 탐색.
- 원본에 기록된 자동 맞춤 축소율과 줄 간격 감소율 읽기.
- 0 높이 표 행, 행 높이 합이 외곽보다 큰 표, 셀 너비·여백·글꼴에 따른 줄바꿈 측정, 병합·세로쓰기·테두리 클리핑 대응.
- 187종 도형 프리셋과 조절값, 그림 자르기, 기본 그룹 회전·뒤집기.
- 수정하지 않은 원본 개체와 관련 XML·미디어 보존.

### 다음 작업의 직접 근거

| 항목 | 확인 수준 | 현재 근거와 의미 |
| --- | --- | --- |
| 양쪽·분산 정렬 | **코드에서 확인** | `TextParagraph.align`은 left/center/right만 표현한다. `readTextBody()`는 `just`, `justLow`, `dist` 등을 왼쪽 정렬로 읽는다. 실제 PowerPoint 최소 예제로 차이를 먼저 재현한다. |
| 사용자 지정 탭 | **코드에서 확인** | `defTabSz`만 보관하고 개별 `tabLst`를 모델에 반영하지 않는다. 오른쪽·가운데·소수점 탭을 사용한 숫자 열에서 차이가 날 수 있다. |
| 글꼴 대체 | **기존 화면 관찰** | DSU 8·14·15·20장 등에 폭·굵기·줄바꿈 차이가 남아 있다. 현재 글꼴 진단은 family 수준이어서 실제 굵기·기울임·문자별 대체까지 증명하지 못한다. |
| 자동 맞춤 | **코드·지원 범위에서 확인** | 가져올 때 저장된 축소율을 적용하지만, 내용을 편집하거나 너비를 바꾼 뒤 PowerPoint처럼 다시 축소하는 동작은 부족하다. 새로 생성하는 내보내기 경로에서는 `autoHeight`에 따라 `spAutoFit`/`noAutofit`을 쓴다. 무수정 원본 보존 경로와 구분해 검사해야 한다. |
| 차트 내부 배치 | **코드 및 기존 화면 관찰** | 범례 폭을 문자 수로 추정하고 제목·축 여백에 고정 계산을 사용한다. `manualLayout`을 해석하는 경로가 확인되지 않는다. Dickinson 4장 등에 plot 영역 차이가 기록돼 있다. |
| 비균일 배율의 회전 그룹 | **명시된 지원 한계** | 현재 개체 모델로 shear, 즉 비스듬한 변형을 완전히 표현하지 못해 가져오기 경고가 있다. |
| 도형 내부 그림·패턴 채움 | **코드에서 확인** | 도형의 `blipFill`/`pattFill`은 제한이 있다. 이미 지원하는 슬라이드 그림 배경이나 일반 그림 개체와 구분한다. |
| 표가 필요 이상으로 커짐 | **검증할 가설** | 현재 행 높이는 원본 높이와 Chromium 측정 높이 중 큰 값을 사용한다. 대체 글꼴이나 줄 간격 차이가 확장을 유발하는지 실측이 필요하다. 아직 새 결함으로 확정하지 않는다. |
| 반투명 색 차이 | **기존 관찰, 원인 미확정** | DSU 13장 녹색 원은 RGB·alpha가 원본 XML과 같은데 화면색이 조금 달랐다. 파서 문제로 단정하지 않고 배경 합성·색공간·캡처 조건을 조사한다. |

## 3. PowerPoint 비교 기준과 시험 자료

### 비교 환경

1. 이전 요청과 비교 자료를 이어서 **웹 PowerPoint를 기본 시각 기준**으로 사용한다. OS, 브라우저 버전, 캡처 날짜, 배율, DPI, 슬라이드 비율, 글꼴 상태를 함께 기록한다.
2. Windows 데스크톱 PowerPoint는 별도 검증 경로로 둔다. 웹과 데스크톱 결과가 다르면 각각 기록하고, 유리한 쪽의 결과를 섞어 통과시키지 않는다. 사용할 수 없으면 미검증으로 표시한다.
3. LibreOffice 출력은 보조 진단에 사용한다. PowerPoint 일치의 최종 기준으로 사용하지 않는다.
4. 슬라이드 영역만 잘라 같은 크기와 종횡비로 비교한다. UI 테두리·선택 핸들·캐럿은 제외하고 글꼴과 이미지 로딩을 기다린다. 애니메이션이 있는 자료는 같은 정지 시점을 사용한다.
5. 화면 캡처와 PDF 출력 비교는 별도 결과로 관리한다. PDF를 다시 그린 화면과 편집기 화면의 안티앨리어싱 차이를 레이아웃 오류로 취급하지 않는다.

### 자료 구성

- **기존 62장**: 파일 SHA-256을 검증해 재사용하고 현재 버전으로 다시 렌더링한다. 이미지로만 구성된 슬라이드는 별도 집계한다.
- **PowerPoint에서 만든 최소 예제 30~40장 목표**: 한 장에 하나의 속성 또는 작은 조합만 넣어 기대 동작을 명확히 한다. 합성 XML 검사와 실제 PowerPoint 작성·저장 예제를 함께 쓴다.
- **실무형 5~8개 목표**: 한글 보고서, 브랜드 템플릿, 재무표, 혼합 차트, 그룹 도식, 사진 중심 자료를 포함한다. 기존 공개 자료로 충족하면 추가 다운로드하지 않는다.
- **대용량 자료**: 보유 중인 151장 자료와 표·차트가 많은 시험 자료를 재사용한다. 작은 문서의 정확도 수정이 큰 문서 성능을 악화시키는지 확인한다.
- 공개 샘플·시험용 복사본은 기존 업로드 허용 범위에서 웹 PowerPoint로 비교한다. 개인·회사 문서는 별도 허용 없이 업로드하지 않는다.

### 비교 도구 정리

기존 `scripts/qa-corpus.mjs`는 가져오기, 잘림·겹침 후보, 성능, 자체 저장 왕복을 검사한다. **Microsoft 화면과 자동 대조하는 도구는 아니다.** 같은 importer/exporter의 잘못된 가정이 왕복 검사를 통과할 수 있으므로 독립 기준을 추가해야 한다.

현재 `qa/results/.../comparison-review/build_comparison.py`를 바탕으로, 고정 manifest를 입력받는 비교 도구를 추적 가능한 `scripts/` 아래에 정리한다. 이전 캡처 폴더를 수동 지정하는 의존성도 없앤다. 다음 항목을 출력한다.

- 원본 PowerPoint / 수정 전 앱 / 수정 후 앱 / 저장 후 PowerPoint의 나란히 보기, 겹쳐 보기, 차이 이미지.
- 파일 해시, 슬라이드 번호, 소스 개체 ID, 원본 XML 위치, 실제 글꼴, 줄별 문자 범위, 개체 경계와 기준선.
- 차이 분류: 가져오기 속성 손실 / 글꼴 대체 / 화면 배치 / 저장 손실 / 미지원 효과 / 비교 환경 차이.
- 재현 절차, 중요도, 수정 커밋, 동일 시나리오 재검증 결과.

캡처는 슬라이드 경계만 정렬한다. 개체마다 위치를 옮겨 차이를 감추지 않는다. 픽셀 diff와 SSIM은 검토 순서를 정하는 보조 수단으로 쓰고, 하나의 수치를 전체 호환성 퍼센트로 발표하지 않는다.

## 4. 단계별 구현 계획

### A. 비교 기준 고정 — 최우선, 4~8시간

**작업:** 보유 자료·해시·기준 화면을 점검하고, 62장 중 글꼴·표·차트·그룹을 포함한 대표 12장을 현재 버전에서 먼저 비교한다. 전체 62장 자동 렌더링을 연결하고 가장 큰 차이 10건을 분류한다. 양쪽 정렬과 명시 탭은 새 PowerPoint 최소 예제로 재현한다.

**산출물:** 비교 manifest, 재현 목록, 최초 비교판, 환경·글꼴 기록. 기존 오류와 새 회귀를 구분한 작업 순서.

**완료 기준:** 모든 우선 결함에 원본·현재 앱 화면, 원본 속성, 재현 절차가 있고 비교 불가능한 항목은 이유가 표시된다.

### B. 글꼴·문단 정렬·탭 — 우선순위 1, 16~28시간

**주요 파일:** `src/types.ts`, `src/pptx-text.ts`, `src/TextContent.tsx`, `src/text-layout.ts`, `src/text-geometry.ts`, `src/text-validation.ts`, `src/document-fonts.ts`, `src/local-fonts.ts`, `src/pptx-export-layout.ts`.

1. 양쪽 정렬과 분산 정렬을 서로 구분해 모델에 보관한다. 마지막 줄, 한글·영문 혼합, 명시 줄바꿈의 배치를 PowerPoint와 비교한다. CSS `justify` 하나로 모든 모드를 같게 처리하지 않는다.
2. `tabLst`의 위치·정렬을 읽고 보존한다. 왼쪽·가운데·오른쪽·소수점 탭을 작은 예제부터 구현한다. 사용자 입력, 붙여넣기, 서식 변경, 내보내기까지 같은 의미를 유지한다. 문단 속성의 우선순위와 자식 항목은 [Microsoft ParagraphProperties 문서](https://learn.microsoft.com/en-us/dotnet/api/documentformat.openxml.drawing.paragraphproperties?view=openxml-3.0.1)를 기준으로 확인한다.
3. 개발용 진단에서 요청 family와 **실제로 사용된 face·굵기·기울임·문자 범위**를 기록한다. 실제 face를 확인할 수 없는 환경은 추정과 확인을 구분한다. family 존재만으로 일치 판정을 내리지 않는다.
4. 원본 글꼴이 있는 조건과 없는 조건을 별도 시험한다. Calibri/Carlito, 맑은 고딕과 한글 대체 글꼴의 차이를 파서 오류와 분리한다. 특정 제목을 맞추려고 문서 전체 글꼴 폭·굵기·원본 크기를 바꾸지 않는다.
5. 혼합 글자 크기, 위첨자·아래첨자, 빈 문단, 고정/비율 줄 간격, 목록 내어쓰기, 문장부호의 실제 기준선과 줄 수를 계측한다. 먼저 좁은 사례를 고친 뒤 영향을 받는 전체 문단·표를 검사한다.

**회귀 재사용:** `paragraph-layout`, `text-wrapping`, `web-layout-text`, `office-fonts`, `mixed-font-selection`, `round-shape-layout` 검사. 새 정렬·탭 속성은 검증기, 복사·붙여넣기, 실행 취소, PPTX 저장 경로에도 연결한다.

**완료 기준:** 수정 대상 최소 예제는 동일 글꼴 조건에서 줄 수·줄별 문자 범위·탭 기준점이 일치한다. 부분 선택 서식과 한글 입력이 유지되고, 저장 후 PowerPoint에서도 정렬·탭 속성이 남는다.

### C. 자동 맞춤과 원본 값·계산 값 분리 — 우선순위 1, 12~20시간

**주요 파일:** `src/pptx-text.ts`, `src/types.ts`, `src/TextContent.tsx`, `src/text-geometry.ts`, `src/EditableText.tsx`, `src/pptx-export-layout.ts`, `src/pptx-preservation.ts`.

1. `noAutofit`(고정), `normAutofit`(글자 축소), `spAutoFit`(상자 확장)을 모델에서 구분한다. 원래 글자 크기·상자 크기와 현재 표시용 축소율·줄 간격 계산값을 분리한다.
2. 원본에 저장된 `fontScale`·`lnSpcReduction`을 유지하고, 텍스트·너비·글꼴 변경 시 필요한 범위만 다시 계산한다. 축소율을 매번 원래 크기에 적용해 반복 편집 시 누적 축소가 생기지 않게 한다. 속성의 의미는 [Microsoft NormalAutoFit 문서](https://learn.microsoft.com/en-us/dotnet/api/documentformat.openxml.drawing.normalautofit?view=openxml-3.0.1)를 따른다.
3. 편집·발표·축소판·PDF·표 셀 측정이 동일한 문단 배치 규칙을 사용하게 한다. 기존 공통 컴포넌트를 확장하고, 별도 엔진을 한 번에 전면 교체하지 않는다.
4. 계산 캐시는 내용·글꼴 face·스타일·상자 너비·여백·단 수·쓰기 방향을 키에 반영한다. 글꼴 로딩/교체 시 무효화하고, 문서를 닫으면 해제한다.
5. 조회 중 계산이나 글꼴 로딩은 수정 상태·자동 저장·Undo 항목을 만들지 않는다. 사용자가 내용을 바꾸면서 생긴 자동 맞춤은 해당 편집과 한 번에 취소된다.

**완료 기준:** 긴 문장 입력 → 너비 변경 → 실행 취소/다시 실행 → 저장 → PowerPoint 재열기를 통과한다. 고정 상자는 원본 의도대로 유지하고, 자동 확장을 모든 가져온 상자에 일괄 적용하지 않는다.

### D. 상속과 표 높이 — 우선순위 2, 8~16시간

**주요 파일:** `src/io.ts`, `src/pptx-text.ts`, `src/table-layout.tsx`, `src/pptx-table-style.ts`, `src/table-borders.ts`, `src/drawingml-color.ts`.

1. 슬라이드·레이아웃·마스터·테마에서 최종 속성이 결정된 출처를 진단 가능하게 한다. 위치·크기·텍스트·색·선마다 상속 규칙을 검증하고, 하나의 단순 우선순위로 모든 속성을 덮지 않는다. 마스터의 공통 개체와 텍스트 스타일 구조는 [Microsoft SlideMaster 문서](https://learn.microsoft.com/en-us/office/open-xml/presentation/working-with-slide-masters)를 참고한다.
2. 자리표시자의 생략된 `idx`, 부분 좌표 상속, 숨김, 배경 이미지 관계를 조합한 예제를 추가한다. 이미 수정한 사진 누락이 재발하지 않는지 확인한다.
3. 표는 같은 원본 글꼴에서 원본 행 높이·셀 너비·여백·실제 줄바꿈을 함께 비교한다. 대체 글꼴 때문에 커진 표는 원인 표시를 남기고, 단순히 행 높이를 줄여 맞추지 않는다.
4. **외곽 72pt + 32pt 행 4개 → 전체 128pt 이상 유지**, 0 높이 행, 병합 셀, 세로쓰기, 굵은 외곽선 검사를 계속 통과시킨다. 기존의 내용 보호 요구를 레이아웃 정밀화 과정에서 되돌리지 않는다.
5. 원본 높이와 가져오기 복원 높이를 구분하는 정보가 필요한지 검토한다. 무수정 저장 시 원본 보존, 내용 편집 후 실제 높이 저장의 경계를 명확히 한다.

**완료 기준:** 원본에 없는 누락·잘림·테두리 손상이 없고, 확장된 행은 어느 셀·속성 때문에 커졌는지 설명할 수 있다. 텍스트 엔진 수정 후 표 전체가 불필요하게 확대되는 회귀가 없어야 한다.

### E. 차트 내부 배치 — 우선순위 2, 8~16시간

**주요 파일:** `src/chart.ts`, `src/ChartVisual.tsx`, `src/pptx-chart.ts`, `src/chart-image.ts`.

1. plot 영역·제목·범례 등에 기록된 `c:manualLayout`을 먼저 해석한다. 위치·크기의 상대 기준과 mode를 구분한다. [Microsoft ManualLayout 문서](https://learn.microsoft.com/en-us/dotnet/api/documentformat.openxml.drawing.charts.manuallayout?view=openxml-3.0.1)에 정의된 항목을 실제 PowerPoint 예제로 검증한다.
2. 명시 좌표가 없으면 실제 글꼴로 라벨·제목·범례 폭을 측정한다. 문자 수에 상수를 곱하는 범례 폭과 고정 여백을 단계적으로 교체한다.
3. 먼저 막대·선·원형·산점도를 대상으로 축 눈금, 긴 한글 범례, 숫자 형식, 라벨 겹침과 plot 영역을 맞춘다. 기본 레이더의 기존 검증 범위도 유지한다.
4. 차트 표시를 고치더라도 원본 XML·데이터·통합 문서를 불필요하게 재작성하지 않는다. 이중축·3D 등 별도 구현이 필요한 형식은 지원 범위와 미리보기 한계를 유지한다.

**완료 기준:** Dickinson 4장 등 기존 차트 차이를 다시 비교하고, 수동 배치 예제의 위치·크기를 맞춘다. 자동 배치는 잘림·새 겹침 없이 기준 오차를 줄이고, 저장 후 차트 데이터가 유지된다.

### F. 복합 도형·그룹·효과 — 우선순위 3, 16~28시간

**주요 파일:** `src/io.ts`, `src/types.ts`, `src/shape-presets.ts`, `src/drawing-path.ts`, `src/SlideCanvas.tsx`, `src/pptx-preservation.ts` 및 개체 선택·변환·내보내기 경로.

1. 기존 187종 프리셋·조절값 검사는 유지하고, 자주 쓰는 도형 20~30종에 실제 PowerPoint 렌더 기준을 추가한다. 삼각형 꼭지점, 굵은 화살표, 도넛, 연결선, 여러 종횡비를 우선한다.
2. 회전과 비균일 그룹 배율이 함께 있는 최소 예제로 shear 차이를 재현한다. 필요한 경우 2D affine 행렬을 도입하되 화면뿐 아니라 선택 경계, hit-test, 마우스 이동, 크기 변경, 그룹 해제, PPTX 저장까지 설계한다.
3. 그룹 배율을 원본 글자 크기에 다시 곱하지 않는다. 기존 CMU 자료의 글자 크기 보정 사례를 회귀에 포함한다.
4. 도형 내부 그림·패턴 채움을 우선 추가한다. 기존 그림 배경·자르기 구현을 재사용하되, 도형 경로로 잘라 표시하고 원본 이미지를 보존한다.
5. DSU 13장의 색 차이는 RGB·alpha뿐 아니라 밑에 있는 개체와 배경, 합성 순서, 색공간을 조사한다. 원인이 확인되기 전 색 값을 임의로 바꾸지 않는다.

**완료 기준:** 선택한 최소 예제의 화면과 선택 영역이 일치하며 편집·저장 후 변환이 유지된다. 전체 affine 편집이 예상보다 커지면 별도 단계로 분리한다. 내부 그림자·반사·발광·3D 전체 구현은 이 공수에 포함하지 않는다.

## 5. 모든 단계에 적용할 저장·편집 검증

각 수정은 아래 흐름을 모두 통과해야 한다. 원본 파일은 보존하고 시험용 복사본에 작업한다.

| 흐름 | 확인할 것 |
| --- | --- |
| 원본 → Slide Studio 열기 | 최초 화면, 줄바꿈, 개체 누락, 원본에 없던 잘림·겹침 |
| 원본 → 무수정 저장 → PowerPoint 열기 | 복구 경고, 원본 외관, 글꼴·마스터·관계·미디어 보존 |
| 한 개체/문단 편집 → 저장 → PowerPoint 열기 | 의도한 부분만 변경되고 주변 개체·특수 속성이 유지되는지 |
| 앱에서 저장·재열기 3회 → PowerPoint 열기 | 줄바꿈·위치 누적 변화, 테마·마스터·미디어 중복 증가 |
| 부분 선택 서식·Undo/Redo·한글 입력 | 레이아웃 모델 확장이 기존 편집 UX를 깨뜨리지 않는지 |
| 발표·축소판·PDF·인쇄 미리보기 | 편집 화면과 같은 내용·배치인지 |

원본 XML 보존 성공과 앱의 표시 정확도는 별도 항목이다. 수정된 개체가 생성 경로로 바뀔 때 속성이 빠지는지도 확인한다. 새 필드는 입력 검증, 과거 복구 자료 읽기, 앱 간 클립보드, 저장 비교용 fingerprint까지 함께 점검한다.

재사용 검사: `tests/pptx-preservation.spec.ts`, `pptx-compound-preservation.spec.ts`, `pptx-master-themes.spec.ts`, `pptx-xml-order.spec.ts`, `scripts/qa-save-native.cjs`, `scripts/qa-pptx-preservation.cjs`, `scripts/qa-large-workflow.cjs`.

## 6. 완료 판정 기준

아래 수치는 **앞으로 사용할 목표/제안치**이며 현재 달성 결과가 아니다. 위치 허용치는 A 단계에서 반복 캡처·글꼴 조건의 측정 오차를 확인한 뒤 구현 시작 전에 확정한다.

| 항목 | 판정 방법 |
| --- | --- |
| 심각한 오류 | 검증 대상에서 새 텍스트·그림·표 누락, 글자 잘림, 의도하지 않은 겹침, PowerPoint 복구 경고 **0개** |
| 동일 글꼴 텍스트 | 수정 대상 최소 예제의 줄 수와 각 줄의 문자 범위 일치. 기준선과 탭 위치 오차는 별도 측정 |
| 위치·크기 | 초기 제안은 일반 개체 경계·기준선 오차 **1 CSS px @96dpi = 0.75pt 이내**. 미세 선·그림자·글자 잉크는 특성에 맞게 별도 기준 설정 |
| 대체 글꼴 | 원본 글꼴 미보유로 분리 집계. 원문·원본 글꼴명·크기 보존, 대체 상태 표시. 동일 글꼴 일치 항목의 통과 수에 섞지 않음 |
| 차트 | 데이터·계열·숫자 형식 보존, 명시 배치 준수, 새 라벨 잘림·겹침 0. 자동 배치 차이는 영역별 기록 |
| 왕복 저장 | 3회 왕복에서 내용 손실과 예상하지 않은 구조 증가 없음. 자산 해시·관계 유효성·외부 PowerPoint 외관을 함께 확인 |
| 성능 | 같은 기기·자료·글꼴 조건에서 열기·전환·저장 시간과 peak 메모리를 비교. 대표 시간/메모리의 10% 초과 악화는 원인 분석 대상으로 하는 초기 제안이며 측정 잡음을 먼저 확인 |
| 검증 범위 | 실패·생략·미지원·기준 화면 없음 구분. 과거 검사 수를 새 결과로 합산하지 않음 |

성능 측정은 대표 문서에서 최소 5회 시간 측정으로 중앙값과 범위를 기록한다. p95를 보고할 경우 충분한 표본을 따로 확보한다. 메모리는 GC 후 JS heap과 프로세스 전체 peak를 구분하고, 새 문서로 전환한 뒤 회수 여부를 확인한다.

## 7. 공수와 첫 작업 묶음

| 단계 | 예상 실작업 시간 |
| --- | ---: |
| A. 기준·재현 자료 | 4~8시간 |
| B. 글꼴·정렬·탭 | 16~28시간 |
| C. 자동 맞춤·계산 값 분리 | 12~20시간 |
| D. 상속·표 | 8~16시간 |
| E. 차트 | 8~16시간 |
| F. 복합 도형·변환의 제한된 범위 | 16~28시간 |
| 통합 저장·플랫폼·대용량 최종 검증 | 8~16시간 |
| **합계** | **72~132시간** |

단계별 공수에는 해당 기능의 회귀 확인을 포함한다. 이는 실제 PowerPoint 환경을 사용할 수 있다는 전제의 계획치이며, 대기 시간과 전체 렌더링 엔진 교체·전체 affine 편집·고급 Office 효과 구현은 포함하지 않는다. 기준 화면을 다시 확보한 뒤 작업량을 조정한다.

**우선 실행할 묶음은 A + B의 양쪽 정렬 한 종류다.** 대표 12장과 최소 예제로 기준을 만들고, 코드에서 확인한 왼쪽 정렬 변환 문제 하나를 가져오기→표시→편집→저장 전 경로에서 해결한다. 그 결과를 확인한 뒤 분산 정렬·탭·글꼴 계측으로 확장한다. 짧은 첫 작업에서 모든 글꼴과 레이아웃을 해결했다고 판단하지 않는다.

작업 단위마다 재현 자료, 수정, 같은 시나리오 재검증, Git 반영을 완료한다. 실제 앱 교체는 열려 있는 문서와 저장 상태를 확인한 뒤 진행한다. 공개 설치 파일·GitHub Release·리토스 문서 갱신은 별도 배포 요청에 따른다.

## 8. 장기 선택지와 판단 시점

- **문서에 포함된 글꼴 활용:** 로컬 글꼴 진단 이후 검토한다. PPTX 내부 글꼴 형식·크기·사용 범위와 임베딩 권한을 확인하고, 문서 범위에서 사용할 수 있는 경우에 한정한다. 모든 글꼴이 임베딩 가능한 것은 아니고 문자 일부만 포함된 글꼴은 편집에 제약이 있다. [Microsoft 글꼴 임베딩 안내](https://support.microsoft.com/en-us/office/fonts/benefits-of-embedding-custom-fonts)
- **독립적인 정밀 텍스트 배치 엔진:** 같은 원본 face를 사용해도 줄바꿈·기준선 차이가 반복되고 CSS 보정이 복잡해질 때 검토한다. 먼저 줄 계산만 시험하고 기존 한글 입력·선택·접근성·Undo를 보존한다. 새 shaping 라이브러리 도입만으로 PowerPoint의 문단 규칙까지 같아지는 것은 아니다.
- **원본 외관 참고 보기:** 지원하지 못하는 복잡한 장의 PowerPoint 출력 PDF/이미지를 사용자가 제공한 경우 편집 화면과 대조하는 기능을 검토할 수 있다. 참고 이미지가 자동으로 편집 가능한 개체를 대신하지 않도록 한다.
- **고급 차트·SmartArt·Office 효과:** 실제 검수 자료에서 빈도와 피해가 큰 순서로 별도 계획한다. 원본 패키지 보존과 화면 지원을 분리해 확장한다.
