# 대용량 문서 실사용 검수 — 2026-10-22

대용량 실제 PPTX 파일을 파일 열기로 불러온 뒤 첫 장·마지막 장·중간 장 이동, 본문 편집, 실행 취소·다시 실행, PPTX 저장, 저장한 파일 다시 열기를 검증했다. 기존의 300장 IndexedDB 입력 테스트에 추가한 파일 입출력 검수다.

## 발견하고 수정한 문제

500장 문서에서 **슬라이드 추가** 또는 `Ctrl/Cmd+M`을 실행하면 501장이 되어 PPTX 저장이 실패했다. 499장 문서에서 두 장을 복사·붙여넣기해도 같은 문제가 발생했다. 실제 저장 버튼에서 `PPTX 저장 실패: 슬라이드는 1–500장이어야 합니다.`를 재현했다.

원인은 가져오기·저장과 기존 슬라이드 복제에는 개수 제한이 있지만, 새 슬라이드 추가와 슬라이드 붙여넣기에는 같은 제한이 없었던 것이다. `src/document-limits.ts`의 공통 기준으로 삽입 전에 검사하도록 수정했다. 제한을 넘는 편집은 기존 문서와 실행 취소 이력을 변경하지 않고 안내한다.

`tests/large-document-limits.spec.ts`의 두 시나리오는 수정 전 모두 실패했고 수정 후 모두 통과했다. 한 장 삭제 후 다시 추가하여 500장으로 만드는 작업, 실행 취소·다시 실행, 실제 PPTX 다운로드도 확인했다. 수정 전 증거는 로컬 `.cache/qa-user-large/limit-bug-before.json`, `limit-bug-before.png` 및 `test-results-limit-before/`에 보관했다.

## 파일별 재검증

환경은 macOS ARM64의 별도 Chrome 프로필, 1440×900 화면이다. 사용자의 실행 중 문서와 프로필은 사용하지 않았다. 혼합 문서는 한글·영문 텍스트, 타원·블록 화살표, 고유 JPEG 그림, 표, 발표자 노트로 구성했다. JPEG는 이미지 압축·메모리 부하를 만들기 위한 합성 난수 이미지다.

| 파일 | 크기 | 개체 / 그림 / 표 | 열기와 복구 버퍼 저장 | PPTX 저장 | 저장한 파일 다시 열기 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 혼합 문서 300장 | 35.5 MiB | 1,860 / 300 / 60 | 2.83초 | 3.01초 | 3.18초 |
| 혼합 문서 500장 | 59.1 MiB | 3,100 / 500 / 100 | 4.83초 | 5.03초 | 4.85초 |
| 공개 CMU 강의 자료 70장 | 191.8 MiB | 325 / 105 / 0 | 3.41초 | 7.07초 | 4.05초 |

각 파일에서 전체 슬라이드 수, 모든 텍스트, 모든 발표자 노트, 표의 셀 내용, 모든 그림 데이터의 SHA-256이 저장 전후 동일한지 비교했다. 모든 파일이 통과했고 브라우저 런타임 오류가 없었다. 첫 장으로 돌아와 텍스트 열 글자를 입력하고, 실행 취소로 원문을 복구한 뒤 다시 실행한 내용까지 저장 후 유지됐다.

추가로 저장한 파일을 반복해서 다시 열었다. 300장과 CMU 파일은 최초 다시 열기 뒤 세 번, 500장 파일은 한 번 더 열어 같은 내용 비교를 통과했다. 강제 GC 뒤 측정한 CMU 파일의 JS 힙은 반복 세 번에서 154.5 → 154.6 → 154.6 MiB였다. 이 반복 범위에서 메모리가 매번 누적되는 현상은 관찰하지 못했다.

## 성능 해석과 남은 한계

- 첫·마지막·중간 장 사이 이동은 약 0.07–0.55초 범위였다. 10자 입력 시간은 300장 1.00초, 500장 1.11초, CMU 0.22초였다. 자동화 명령·확인을 포함한 왕복 시간이며 순수 키 입력 지연을 뜻하지 않는다. 다른 QA 작업과 같은 Mac에서 측정한 값으로, 하드웨어 성능 보증이 아니다.
- CMU 파일 저장 중 최대 약 3.17초의 메인 스레드 작업이 관찰됐다. 파일 생성은 끝까지 성공하지만 이 구간에는 UI가 잠시 멈출 수 있다. 워커로 파일 생성 작업을 옮기는 구조 변경은 이번 수정에 포함하지 않았다.
- 500장 문서에서는 썸네일과 인쇄용 표시를 포함해 약 15만 DOM 노드를 유지한다. 시험한 문서는 편집·저장 가능했지만 더 느린 PC의 성능이나 장시간 사용까지 보증하지 않는다.
- 이 항목은 렌더러의 실제 파일 입력·다운로드 검수다. Windows/Linux 설치 앱, 실제 OS 파일 선택 창, 모든 슬라이드의 PowerPoint와 픽셀 단위 일치는 별도 검수 범위다.

## 재현 명령과 결과

개발 서버 `npm run dev`를 실행한 상태에서 다음 명령으로 재현한다. 파일 생성·저장 결과와 측정 JSON, 다시 연 첫 장 스크린샷은 지정한 `.cache` 경로에만 저장된다.

```sh
npx playwright test tests/large-document-limits.spec.ts --output=.cache/qa-user-large/test-results-limit-after
QA_LARGE_REOPEN=3 node scripts/qa-large-workflow.cjs .cache/qa-user-large-final all
QA_LARGE_SLIDES=500 QA_LARGE_REOPEN=1 node scripts/qa-large-workflow.cjs .cache/qa-user-large-final generated
```

`all`은 `qa/samples/cmu-lecture-1.pptx`가 있는 경우에 실행한다. `generated`는 외부 샘플 없이 합성 문서만 검사한다. 생성 PPTX와 다운로드 파일은 Git에 추가하지 않는다. 최종 측정 JSON은 `.cache/qa-user-large-final/{mixed-300,mixed-500,cmu-70}/metrics.json`, 런타임 소스 확인값은 같은 경로의 `runtime-sources.sha256`에 있다.

최종 소스 고정 후 세 파일의 전체 시나리오를 다시 실행했고, 실행 전후 변경된 런타임 파일 6개의 SHA-256이 같음을 확인했다. 간추린 최종 결과는 `qa/results/user-workflows/large-300.json`, `large-500.json`, `large-cmu.json`에 복사했다. 이 측정에는 최종 빈 표 셀 서식·투명도 수정과 텍스트 편집 도중 저장 후 실행 취소 이력 수정이 포함되어 있다.
