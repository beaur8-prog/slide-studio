## 변경한 동작

- 원본 PPTX의 일반 양쪽 맞춤 `a:pPr algn="just"`를 모델의 `justify`로 읽고,
  글자·도형 내부 텍스트·표 셀에서 표시·편집·저장한다. 기존 버전은 이를
  왼쪽 정렬로 읽으며 모델에 직접 넣은 `justify`도 검증에서 거부했다.
- **홈 → 양쪽 맞춤**, **Ctrl/⌘+J**, 표 편집의 가로 정렬에서 적용한다.
  일부 단어나 Shift+Enter 뒤 구간을 선택해도 정렬은 문단 전체에 적용하며
  원래 선택 범위와 인접 문단의 정렬을 유지한다.
- 빈 문단과 빈 중간 문단에 먼저 정렬을 지정한 뒤 입력할 수 있다. 같은 정렬을
  다시 적용하면 수정 상태와 실행 취소 이력이 늘어나지 않는다.
- 도형 안 텍스트도 실제 글자의 서식을 모델에 반영한다. 긴 입력·정렬 이력의
  실행 취소 뒤 정렬이 저장값과 달라지던 경로를 보완했고, 부분 기울임을 함께
  사용해도 도형의 채우기·선·위치·크기를 유지한다.
- 편집을 마친 개체의 정렬 버튼은 문단의 실제 정렬을 반영한다. 여러 문단의
  정렬이 서로 다르면 어느 한 버튼을 켜진 것으로 표시하지 않는다.
- 새 정렬 버튼을 추가한 홈 메뉴는 최소 지원 폭 970px부터 1540px까지,
  1040/1041px·1200/1201px 등 반응형 경계에서도 가로로 넘치지 않게 조정했다.
- 문단에 직접 정렬이 없을 때 PPTX 저장은 `문단 → 개체 → 왼쪽`의 기본값을
  사용한다. 기존 생성 경로가 개체의 기본 정렬을 무시하던 부분도 보완했다.
- 표·셀의 입력 검증, HTML과 Studio 표 클립보드, 서식 복사의 정렬 판독에
  `justify`를 연결했다. 일반 양쪽 맞춤에 대한 원본 서식 손실 경고를 제거했고,
  `dist`·`justLow`·`thaiDist`의 기존 지원 제한과 편집 경고는 유지한다.
- 공개 CMU 자료의 그림 테두리 누락을 재현하고 가져오기·표시·생성 PPTX 저장을
  보완했다. 단색 선의 테마 색·두께·투명도·점선·끝 모양을 유지한다. 자르기는
  그림 내용만 클리핑하며 선은 그림의 투명도와 별도로 그린다. 배경 그림은
  공용 표시 컴포넌트에서 투명도가 중복 적용되지 않도록 한다.

편집 중 정렬은 원본 문단 전체를 잠시 선택해 브라우저의 네이티브 정렬 명령을
실행한 뒤 사용자의 선택을 복원한다. 문단 HTML을 통째로 바꾸면 빈 문단에서
중첩 구조가 생길 수 있어, 정렬은 기존 블록을 유지하는 경로를 사용한다.
실행 취소 후에는 실제 글자·빈 블록의 정렬을 다시 읽는다. 작은 DOM 스냅샷
캐시에만 의존하면 긴 편집 이력에서 화면과 저장값이 달라지는 문제가 있었다.

## 재현과 검증

새 `tests/paragraph-justify.spec.ts` **19개 통과**:

- 직접·목록/레이아웃 상속·명시적 왼쪽 override 가져오기.
- 개체 기본 정렬, 생성 표·클립보드, 편집 후 3회 PPTX 저장과 재열기.
- 부분 선택·단축키·빈 문단·중간 빈 문단·Shift+Enter와 네이티브 Undo/Redo.
- 일반 텍스트와 도형에서 입력·정렬을 14회 섞은 뒤 28회 Undo의 화면·저장 정렬 일치.
- 한글·영문의 자동 줄바꿈에서 오른쪽 끝과 마지막 줄의 자연 너비.
- 개체 선택의 정렬 버튼 상태, 도형 부분 기울임·정렬의 저장과 외관 속성 유지.
- 미지원 정렬 3종의 무수정 원본 보존과 편집 시 제한 안내.

기존 부분 서식·문단 간격·혼합 글꼴·표 선택 관련 **23개**도 통과했다.
수정 전 실제 기준 서버에서 `just → left`와 `justify` 검증 거부를 재현했다.
수정 과정의 빈 문단 중첩·긴 Undo 문제도 실패 결과를 보관한 뒤 같은 검사로
해결을 확인했다. 초기 캐시 오류와 검사 자체의 잘못된 기대값은 제품 결함과
구분해 기록했다.

공개 합성 5장 원본은 `scripts/create-justify-fixture.mjs`로 만든다. 원본과
3회 편집 저장본은 Office OOXML 스키마 검증을 통과했고, 같은 앱에서 다시 그린
5장 화면도 같았다. 이는 독립 PowerPoint 렌더와의 일치 증거는 아니다.

실제 Mac 패키지의 `scripts/qa-justify-native.cjs`는 다음 5개 흐름을 통과했다.

1. 직접 양쪽 맞춤 원본 열기.
2. 부분 선택 → 정렬 → 네이티브 메뉴 Undo/Redo 및 같은 정렬 재적용.
3. 실제 파일 IPC로 다른 이름 저장·재열기 3회와 표준 `algn="just"` XML 확인.
4. Production PDF 출력, 원본 파일 해시 보존, 페이지 오류 0개.
5. 도형 입력·정렬 14회 → 네이티브 메뉴 Undo 28회에서 실제 글자 노드의 정렬,
   저장 문자열·정렬을 매번 비교. 도형 속성을 유지하고 별도 PPTX 저장·재열기 확인.

Mac 검수 환경은 Electron 42.11.15 / Chromium 148.0.7778.280 / arm64다.
개인 문서와 다른 임시 프로필을 사용했으며 OS 선택창의 응답만 검수용으로
공급했다. 현재 Mac 잠금으로 실제 OS 선택창 조작과 사용자 앱 교체는 진행하지
않았다. 종이 출력과 실제 Windows/Linux 앱 검증은 이 Mac 결과에 포함하지 않는다.

타입 검사·production 빌드·Mac 패키지 ad hoc 서명 검증을 통과했다.
패키지의 배포용 `dist/`·`electron/` 파일 63개가 빌드 입력과 일치하는지도
SHA-256으로 확인했다. 앱 manifest는 개발 의존성·스크립트를 제외한 의도된
배포 형식이며 버전·진입점 등 필요한 필드는 원본과 같다.

그림 테두리의 새 회귀 **6개**와 GIF·자르기·교체·배경·duotone·그림 자리표시자·
Strict OOXML 등을 합친 관련 **54개**는 모두 통과했다. 자르기 경계 밖의
테두리와 독립 투명도는 실제 픽셀로 확인했다. 실제 Electron production
renderer에서 이동 편집 → 저장·재열기 3회 → PDF 출력을 통과했고, 원본과
3회 저장본 총 4파일은 OOXML 스키마를 통과했다. PDF를 이미지로 렌더링해
색·점선·굵은 테두리·그림 투명도를 육안 검토했다.

첫 전체 검사 789개는 768개 통과·6개 조건부 생략·15개 실패였다. 13개는 기존
Mac 파일 선택창 모의 객체의 API 누락으로, 수정 전 `fd5a04c`에서도 재현했다.
1개는 새로 지원한 `justify`를 잘못된 값으로 기대하던 표 검증, 1개는 홈 메뉴의
가로 넘침이었다. 모의 객체·기대값과 실제 메뉴를 각각 보완했다. 네이티브
