# Windows memory verification — 2026-10-17

## Confirmed retention and fix

The root `App` previously kept the full saved-document list in its `library`
state after the library dialog closed. Each deck includes embedded images, so
the retained heap grew with the size of the saved workspace. Reopening replaced
the list; it was persistent unnecessary retention, rather than another copy on
every open. IndexedDB archives themselves are intentional user data.

`LibraryContents` now owns that list only while mounted. Closing, Escape,
backdrop dismissal, selecting a document, and starting a new document all
unmount it. A disposed flag also ignores a read that completes after dismissal.
No saved documents are deleted.

The fixture contains 12 saved decks with approximately 13.77 MiB of encoded PNG
payloads on their second slides. The first slides are empty, so preview image
decoder caches do not account for this test's retained JavaScript data.

| Production Electron state, after renderer GC | Before | After |
| --- | ---: | ---: |
| Seeded workspace, library not opened | 4.60 MiB | 4.59 MiB |
| Library closed, third repetition | 18.70 MiB | 4.91 MiB |
| Small document loaded afterward | 18.72 MiB | 4.92 MiB |

Measurements use the production Vite bundle and Electron 42.11.15 on Windows,
with a separate temporary app-data directory. The existing user workspace is
not used by stress tests. Each idle sample follows autosave and two explicit
renderer collections. Values are JavaScript heap usage, not total application
RAM.

`tests/library-memory.spec.ts` reproduces the old failure (about 14.5 MB of
additional retained heap), checks all five dismissal paths, and delays an
IndexedDB response until after closing. The fixed browser regression run retained
only 0.04–0.49 MB over its baseline across the five paths; the late-read case
returned to its baseline. Its 5 MiB tolerance distinguishes the large document
payload from browser/framework warm-up.

## Repeated operations

The public 22-slide DSU deck was used for 100 presentation enter/navigate/black
screen/exit cycles. Between cycles 10 and 100, renderer heap stayed within
11.12–11.28 MiB, DOM nodes stayed at 10,825, and listeners stayed at 495. The
single Electron window and main IPC listener counts did not accumulate.

A separate test repeatedly imported the 106-slide CMU lecture 4 deck, then
replaced it with a one-slide empty document. Main-process input buffers were
reclaimed by GC. Renderer heap after replacement was about 6.0–6.5 MiB over 30
cycles, with image backing storage approximately 0.94 MiB and 245 listeners.
Native process memory is evaluated separately from these heap measurements.

### Native memory and measurement overhead

The Playwright-controlled run showed renderer private memory increasing from
93.86 to 234.90 MiB over 12 imports. Extending to 30 imports reached a plateau
around 330–340 MiB from approximately cycle 21. This was not treated as proof of
an application leak, because inspector/automation data can sit outside the JS
heap.

A control used the same production app, public PPTX, and isolated profile, but
only Electron's `webContents.debugger` for heap/DOM measurements. It did not
attach Playwright or enable the CDP Network domain. Over 12 imports:

| Small-document idle state | After import 1 | After import 12 |
| --- | ---: | ---: |
| Renderer JS heap | 4.70 MiB | 4.83 MiB |
| DOM nodes | 625 | 625 |
| Event listeners | 232 | 232 |
| Renderer private memory | 79.51 MiB | 97.44 MiB |

After a diagnostic memory-pressure notification and 15 seconds idle, renderer
private memory fell to 82.10 MiB. The notification is confined to this test; the
application does not force garbage collection or clear caches during normal use.
The difference substantially narrows the apparent native growth to measurement
overhead and reclaimable allocations. It does not identify every allocation.

Playwright enables Network tracking. Chromium's inspector keeps response data
in a bounded buffer, making it a plausible contributor to the difference; this
specific mechanism was not isolated by toggling Network within an otherwise
identical session. See the [Chromium inspector implementation](https://chromium.googlesource.com/chromium/src/+/6c5f5ee0b475b53a51865f72dc2fdc40d3d3605f/third_party/blink/renderer/core/inspector/inspector_network_agent.cc).
No additional accumulating document, DOM, listener, or window leak was found in
these measured scenarios.

## Scope and reproduction

`npm run build` passed, and the complete regression suite passed **90/90** in
7.3 minutes, including the two new heap-retention tests. Results are under
`qa/results/windows-memory-tests/`. The Windows package was rebuilt, installed
with its ASAR hash verified, and launched. The existing saved 15-slide document
was restored and returned to its previously selected third slide.

Run the committed regression with:

```sh
npm ci
npx playwright test tests/library-memory.spec.ts
```

Local stress scripts and raw samples are under the ignored
`research/memory-review/` directory (`before-library`, `after-library`,
`before-presentation-real`, `before-io`, `before-io-30`, and `native-io`). Public sample
decks are obtained with `scripts/fetch-qa-samples.py` and are not redistributed.

Source review covered event listeners, ResizeObserver/font callbacks, preload
IPC subscriptions, object URLs, undo history, import caches, TIFF canvas buffers,
IndexedDB connections, and Electron windows. Import/export and TIFF conversion
can temporarily use substantially more memory than their compressed files.
Undo history intentionally retains up to 60 edit states. Finite stress tests do
not prove the absence of every possible leak or replace a long-duration soak.

The earlier PowerPoint native analysis describes PowerPoint's implementation;
it is not evidence about this Electron application's allocator behavior.

`e8b46b55115714bef8ccb18b76ea8b7abff65e2820ffe62a045257721129b0cc`.
